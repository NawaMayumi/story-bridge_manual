01

目的

何のために、誰のために作っているか

Inventory Management Systemは、学校の共有備品を、先生の端末とGoogle Sheetsだけでやりとりする貸出・返却アプリです。物品名と数量を声か文字で伝えると貸出が記録され、返すときは保管場所を確認して写真を撮るだけで返却が完了します。

目指しているのは、先生たちが共有物品を必要なときにすぐ使え、かつ「物品管理」という余計な仕事を背負わずに済んでいる状態です。「どこにあるか」「何個あるか」「誰が持っているか」を誰にも聞かずその場で分かること、そして物品がどんな状態かを写真で確認できることが、活動を円滑に始め、円滑に終えるための土台になります。

学校の保管場所は校内に分散しており、それぞれに専用の端末を置くことはできません。そのためこのアプリは、先生が普段使っているスマートフォンやChromebookだけで完結するように作られています。借りるときはカメラを使わず音声・文字入力を中心にし、返すときだけ写真を撮って次に使う人への目印を残します。開発はAHISインターンでの制作で、新しくできる学校での利用を見据えています。

02

仕組み

画面の裏側で、実際に何が動いているか

データの正式な保管場所はGoogle Sheetsで、Items(物品)・Locations(場所)・Users(先生)・Loans(貸出)・Transactions(取引履歴)という5枚のシートがすべての記録を持ちます。画面と業務ロジックはApps Scriptが担当し、返却時の写真だけはGoogle Driveへ保存されます。

カメラ機能だけは別の仕組みです。Apps ScriptのHTML Serviceはiframeの中で動くため、ブラウザの権限ポリシーによって(カメラ起動の命令)が制限されることがあります。そこでカメラ画面だけをCamera Bridgeという別の小さなアプリとして切り出し、Google Cloudの上で動かしています。Camera Bridgeは写真も先生の名前も在庫データも一切扱わず、撮影した画像をJPEGへ縮小してで元の画面に返すだけです。

Borrowの音声入力はカメラと違い、別アプリを介さずApps Scriptの画面内だけで完結します。ブラウザに内蔵されたを直接呼び出し、認識結果をその場でテキスト欄に追記するだけなので、音声データがApps Scriptの外へ出ることも、生成AIへ送られることもありません。

ファイル構成

appscript/Code.js

サーバー側の全ロジック(貸出・返却・在庫計算など)

appscript/Index.html・JavaScript.html・Stylesheet.html

画面のHTML・JS・CSS(Apps Scriptの制約でこの3ファイルに分かれている)

camera-bridge/server.js・public/

カメラ専用の小さなNode.jsアプリ

ルート直下の index.html・app.js・style.css

開発初期のスタンドアロン試作。現在のApps Script版とは同期しておらず、本番のソースではない

Google Driveでの保管

ソースのバックアップは、他のAHISプロトタイプ(BlockBlock、PictureBook Creationなど)と共通の01_Private / 02_Published / 03_Systemという構成に合わせています。03_Systemにappscript・camera-bridgeと引き継ぎガイド一式を保管し、01_Privateは相手校には渡さない内部メモや試験用データに使います。Inventoryには本や成果物のような「完成品として公開するファイル」に相当するものがないため、02_Publishedは他のプロジェクトほど使いません。

コードを更新したいとき

物品・場所・先生の追加はSpreadsheetかアプリの登録画面で完結し、コードの変更は不要です。画面や業務ロジックそのものを変えたいときは、Apps Scriptのエディタ(script.google.com)を開き、対応するGoogle Workspaceライセンスがあれば内蔵のに自然言語で修正を頼めます。外部のエンジニアがいなくても、エディタを開ける担当者がその場でコードを直せる経路です。

対応ライセンス

Business Standard/Plus・Enterprise Standard/Plus・Workspace Gemini Add-on・Google AI Pro for Education のいずれか

有効化

Google Workspace管理者がAdmin Consoleで生成AI機能をオンにする必要がある

反映前の確認

Geminiが生成したコードも、Apps Scriptで一度実行し、validateP4Data()で issues: 0 になることを確認してからデプロイする

03

できること

今、実際に動いている4つの中心機能

Borrow

物品名と数量を、画面内の録音ボタン(端末のマイクで直接認識)または端末キーボードのディクテーション、文字入力のいずれかで伝える。曖昧な場合はItemsの正式候補から先生が選ぶ。確認後にLoansとTransactionsへ記録し、在庫を自動で減らす。

Return

借りている物品と数量を選び、本来の保管場所を大きく表示。別の場所に置いた場合だけメモを追加し、最後にCamera Bridgeで写真を撮って完了する。

Hand Off

貸出中の物品を、その場で別の先生へ引き継ぐ。渡す物品と数量を選び受け取る先生を選ぶと、Loan(貸出記録)の責任者だけが切り替わり、以後の返却は新しい持ち主が行う。

Inventory

カードで在庫数・保管場所・最新メモを一覧表示。カードを押すと物品ごとの貸出・返却履歴と直近5枚の返却写真を確認でき、新しい物品や保管場所もその場で登録できる。

04

まだ足りないこと

重要度順に並べています。上にあるものほど、実際に学校で使う前に確認・対応が必要です。

最優先 重要 今後検討

Camera Bridgeが期限付きアカウントで稼働中

最優先

Camera Bridgeは、開発担当(名和真結美)個人のアカウントに紐づいたGoogle Cloudプロジェクトの上で動く想定です。このアカウントは3ヶ月間の期限付きのため、期限が切れる前に、学校側が長期的に管理できるGoogle Cloudプロジェクトへ切り替える必要があります。

対応: 切り替えても先生側が使うWeb AppのURLは変わらず、Script Propertiesの値を書き換えるだけで済みます。手順は下の「切り替え手順を見る」から確認できます。

切り替え手順を見る学校の正式運用に移す前に、必ずこの手順で学校用のプロジェクトへ切り替えてください 必ず対応 ▸
  1. 学校側にGoogle Cloudプロジェクトを作ってもらう学校側の管理者に、新しいGoogle Cloudプロジェクトを作成し、Billingを有効にしてもらう。
  2. 必要なAPIを有効にするそのプロジェクトでCloud Run・Cloud Build・Artifact RegistryのAPIを有効にする。
  3. ソースを用意するcamera-bridge/フォルダをCloud Shellへアップロードする(またはソース保管用のGoogle Driveからダウンロードして使う)。
  4. デプロイするフォルダの中で次のコマンドを実行する。 
    gcloud config set project TARGET_PROJECT_ID
gcloud run deploy ahis-camera-bridge \
  --source . \
  --region asia-northeast1 \
  --allow-unauthenticated
  5. URLを確認する発行されたhttps://...run.app URLを控え、/healthzを開いてokが返ることを確認する。
  6. Apps Script側のURLを書き換えるApps Scriptエディタの「プロジェクトの設定」→「スクリプトプロパティ」で、CAMERA_BRIDGE_URLを新しいURLに書き換える。
  7. 実機で確認するWeb Appを開き直し、返却時のカメラが新しいCloud Run上で正しく動くことを確認する。
  8. 古いサービスを削除する動作確認が取れたら、元の個人アカウント側のCloud Runサービスは削除してよい。Sheets・Drive・在庫データへのアクセス権はCloud Run側に最初から与えていないため、削除しても他のデータに影響しない。
再デプロイは不要

スクリプトプロパティ(CAMERA_BRIDGE_URL)の変更は、Web Appを新しくデプロイし直さなくても次回の実行からすぐに反映されます。

Borrowの音声入力(実機未検証)

最優先

Borrow画面の物品入力欄に、画面内で完結する録音ボタン(🎙️ Start Recording)を実装しました。ブラウザ内蔵のSpeechRecognitionでその場を認識し、テキスト欄に追記するだけで、外部のサーバーや生成AIには一切送信しません。別アプリを開く必要もなく、物品名と数量だけを扱う画面のため個人情報も含まれません。

残っている確認: これは開発機での動作確認のみです。学校配布のChromebookで実際にマイクの許可・認識精度が問題なく動くかは、まだ実機で確認されていません。

本人認証がデモ用の記憶のみ

重要

初回に選んだuser_idをブラウザのlocalStorageに保存しているだけで、パスワードなどによる本人確認はありません。共用端末では誰でも他の先生になりすませます。

対応: 引き継ぎ先(実習校)のGoogleアカウント運用を確認したうえで、所有者限定のWeb Appアクセス設定に切り替える必要があります。

実データ投入と学校間の引き継ぎ 重要

  • 実際の物品名・別名・数量・単位・保管場所を、Spreadsheetの本番データへ入れ替える。
  • 曖昧な物品名の候補選択、部分返却、消耗品のUsed Up、Hand Offでの部分引き継ぎを実際に使いながら、挙動や文言を調整する。
  • 学校を移す際は所有権を移さず、相手校のアカウントで新しいSpreadsheet・Apps Script・Driveフォルダ・Google Cloudプロジェクトを作り直し、Script PropertiesのCAMERA_BRIDGE_URLを向き先ごとに書き換える。
  • 変更のたびに日付付きZIPをDriveへ保存し、Apps Script再反映・Web App新バージョン・Cloud Run再デプロイのどれが必要かを都度確認する。

用語集

本文中でボタンになっている用語のまとめです。印刷して読む場合はこちらをどうぞ。

Cloud Run
Googleが提供する、必要なときだけプログラムを動かすサーバーの仕組み。Camera Bridgeの実行場所として使っている。
getUserMedia()
ブラウザでカメラやマイクを起動するための標準命令。Apps ScriptのiframeやPermissions Policyの制限で動かないことがある。
SpeechRecognition
ブラウザに内蔵された音声認識機能。Borrowの録音ボタンはこれを直接呼び出し、音声データを自分たちのサーバーへ送らずにその場で文字に変換する。
postMessage
別々に開いたブラウザのタブや画面同士で、安全にデータをやり取りする仕組み。撮影した画像を元の画面に返すときに使う。
localStorage
ブラウザ内だけに保存される小さなデータ領域。今回は選んだ先生のuser_idだけを覚えておくのに使っており、本人認証ではない。
Script Properties
Apps Scriptの設定画面に保存する、コードに直接書かない値。CAMERA_BRIDGE_URLやRETURN_PHOTO_FOLDER_IDなどを保管する。
validateP4Data()
Apps Scriptに用意した確認専用の関数。SheetsやIDの不整合を報告するだけで、データを書き換えることはない。
clasp
ローカルのファイルとApps Scriptプロジェクトを同期するコマンドラインツール。
Firebase
Googleが提供する、ログイン機能やリアルタイムデータベースなどをまとめて使えるクラウドサービス。
Geminiサイドパネル
Apps Scriptのエディタに統合された、自然言語でコードの生成・修正・説明を頼めるパネル。2026年にApps Scriptエディタへネイティブ統合された。
